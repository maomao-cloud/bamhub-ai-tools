# 2026-04-27 design-retrospective design

## Summary

设计一个 personal skill，用于在用户手动调用时，从当前会话、当前分支未合并 commits、项目显式规范与代码事实中，提炼**可复用的设计方法论**。该 skill 的核心目标不是复盘当前实现是否“有设计意图”，而是默认当前实现具备明确意图，在我理解不充分时通过结构化追问补全理解，并将结果沉淀为对**下一次需求**和**其他项目**都可迁移的设计原则、pattern 与扩展性建议。

代码风格与个人协作偏好仍然保留，但处于次级位置，只作为补充上下文，而不是主输出。

## Goals

- 在一次手动调用中，基于多来源证据提炼可复用的设计原则。
- 识别本次工作体现出的 pattern、边界划分方式、扩展性考虑与外部调用友好性。
- 在理解不充分时主动向用户追问，并给出 2-3 个候选猜想供选择。
- 输出面向未来需求和跨项目迁移的建议，而不是只面向当前任务做回顾。
- 在发现项目中存在明确团队规范来源时，先询问用户是否纳入本次分析基线。

## Non-Goals

- 不自动触发，不接 hook。
- 不自动写 memory，只提供可选 memory 建议。
- 不直接修改 `CLAUDE.md`、skill 文档或其他规范文件。
- 不做全仓架构评审，只围绕最近这轮工作和相关上下文提炼规律。
- 不把当前实现默认视为缺乏设计意图的问题对象。
- 不把代码格式、命名偏好、提交习惯作为主分析对象。

## Trigger

该 skill 仅在用户显式调用时执行。

当前阶段定位为手动调用的 personal skill，后续可演进到 hook 驱动的自动上下文采集，但这不属于当前范围。

## Inputs

### 1. Current conversation context

读取当前会话的全部上下文，但只提取与以下主题相关的内容：
- 设计意图
- 结构性取舍
- 设计模式或 pattern
- 可扩展性、复用性、外部调用考虑
- 用户对分析方向的纠正与澄清
- 代码风格与协作偏好补充

忽略与这些主题无关的任务噪音。

### 2. Current branch unmerged commits

默认分析当前分支相对于主分支的未合并 commits，作为最近行为证据的主要来源。

该范围用于观察：
- 本次工作里稳定出现的设计取向
- 抽象边界与职责拆分方式
- 为未来扩展预留的接口或层级
- 文档、说明与实现之间的一致性

### 3. Explicit conventions

采用混合模式：先读取显式规范，再用代码事实补充或校正。

优先级：
1. 项目级规范，如 `CLAUDE.md`
2. 与当前工作相关的 skill 文档
3. 其他明确说明型文档

如果扫描到明显的团队规范来源，skill 必须先问用户：

> 是否将这些团队规范纳入本次分析基线？

在当前项目中，`CLAUDE.md` 是明确的团队规范来源；`README.md` 不构成有效规范来源。

### 4. Code facts

从现有代码与最近改动中归纳“实际做法”，用于：
- 补充显式规范未写明的稳定设计惯例
- 校正显式规范与实际实现之间的偏差
- 判断某个 pattern 是偶发还是稳定出现

## Analysis principles

### Default assumption

默认用户当前设计是**有明确意图**的。

如果我不理解某个设计选择，不应把它当作“缺乏设计”，而应把它视为“我尚未正确理解”。

### Primary focus

分析重心应放在以下问题：
- 这次工作体现了哪些可复用设计原则？
- 用到了哪些 pattern、结构思路或边界划分方法？
- 哪些写法是为了未来扩展、复用或外部调用而存在？
- 这些经验如何迁移到下一次需求或其他项目？

### Secondary focus

代码风格、喜好规范、协作偏好仍要保留，但只作为补充区块，不应喧宾夺主。

### Confidence handling

对于高置信度结论，直接输出。

对于低置信度判断，必须通过交互式澄清处理，而不是直接武断归纳。

## Interactive clarification behavior

当设计意图、抽象动机、扩展目标或 pattern 识别存在歧义时，skill 应主动向用户追问。

追问要求：
- 以“帮助我正确提炼可复用方法论”为目的，而不是质疑当前设计。
- 优先给出 2-3 个结构化猜想供用户选择。
- 如果多个猜想都不对，允许用户自行补充。

示例追问形式：
- 我目前有三个理解，请你选最接近的一项：
  1. 这是为了复用
  2. 这是为了给外部调用保留扩展点
  3. 这是为了把项目特有约定与可复用能力分离

追问后的用户确认内容，应优先进入最终结论。

## Output structure

每次调用固定输出 6 个区块：

### 1. Reusable design principles

主输出。提炼本次工作中可迁移到未来需求或其他项目的设计原则。

示例类型：
- 先界定边界，再决定实现细节
- 将项目特有约定与可复用能力解耦
- 为未来自动化或外部调用保留稳定输入输出
- 通过文档与实现对齐降低行为漂移

### 2. Patterns and structural approaches observed

总结本次体现出的 pattern、结构思路或组织方式。

如果能高置信识别出设计模式名称，可以点名；如果证据不足，则应描述为“结构意图”而不是硬贴模式标签。

### 3. Migration guidance for future tasks or other projects

说明这些原则和结构经验如何迁移到：
- 下一次类似需求
- 其他项目中的相似问题
- 后续扩展（例如 hook、自动化、外部调用）

该区块应尽量产出可执行的迁移建议，而非抽象感想。

### 4. Low-confidence areas requiring confirmation

列出仍存在不确定性的设计理解点，并附 2-3 个候选猜想供用户确认。

如果没有低置信点，可以明确写“无”。

### 5. Code style and collaboration preference supplement

补充记录：
- 代码层面的稳定写法
- 当前会话中用户确认的协作偏好
- 本次对话中的关键纠正点

这一部分是辅助信息，不是主分析对象。

### 6. Optional memory suggestions

列出哪些稳定偏好或方法论值得沉淀到 memory，并给出简短理由。

该区块只做建议，不自动写入 memory。

## Execution flow

1. 收集当前会话、当前分支未合并 commits、显式规范、代码事实。
2. 扫描是否存在团队规范来源；如存在，先询问用户是否纳入本次分析。
3. 基于证据先提炼可复用设计原则、pattern 和迁移价值。
4. 标记高置信结论与低置信猜想。
5. 对低置信点使用 2-3 个候选项向用户交互式澄清。
6. 基于用户确认修正最终结论。
7. 按固定 6 区块输出 retrospective。
8. 如有合适内容，再附可选 memory 建议。

## MVP scope

### Included in MVP

- 手动调用
- 当前分支未合并 commits 作为默认分析窗口
- 当前会话全文参与，但只抽取设计相关信息
- 发现团队规范时先询问是否纳入
- 交互式澄清低置信设计理解
- 输出以设计方法论为主、代码风格为辅

### Excluded from MVP

- hook 自动触发
- 自动写 memory
- 自动更新规范文档
- 全仓长期历史分析
- 量化评分体系
- 生成通用代码规范文档

## Success criteria

该 skill 的输出应能够：
- 明确指出本次工作里哪些设计经验可复用。
- 说明哪些结构是为了未来扩展、复用或外部调用而存在。
- 在不理解时通过候选猜想获得用户澄清，而不是做浅层误判。
- 让下一次类似需求可以直接参考其结论。
- 让代码风格与协作偏好保留为有用补充，而不抢占主体。
