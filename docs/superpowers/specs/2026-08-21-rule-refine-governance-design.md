# rule-refine 规则治理优化设计

## 目标

增强 `skills/bamhub/maintenance/rule-refine/SKILL.md` 的规则治理判断能力：将一次会话或改动中出现的经验，先按真实归属分流，再以证据、长期价值和删除测试决定是否进入项目规则。

本次不改变团队共享 skill 的所有权结构，不创建工具私有目录，不自动写入未确认规则。

## 核心决策

### 候选四分流

在现有去重前后，所有候选结论必须先选择唯一落点：

| 落点 | 准入条件 | 不应放入的内容 |
| --- | --- | --- |
| `<repo>/.project/rules/*.md` | 跨任务、长期、可执行的专题约束 | 模块事实、一次性任务决定、通用口号 |
| `<repo>/.project/README.md` | 规则索引、规则优先级、阅读路径、最小项目地图 | 专题规则正文、模块实现细节 |
| `<module>/README.md` | 仅一个独立模块稳定成立的职责、边界、主链路或依赖事实 | 项目级约束、一次性实现过程 |
| 设计/计划或不处理 | 当前任务专属决定、尚未验证的方案、普通常识、临时经验 | 长期项目规则 |

若候选内容同时看似适用于多个位置，优先选择影响范围最小且仍足以指导未来工作的落点。只有真正跨模块且跨任务的约束才能进入 `.project/rules/`。

### 证据门槛

候选规则必须标记为三类之一：

- **事实规则**：由当前代码、配置、测试或稳定文档证明；输出中必须写明证据文件或材料。
- **决策规则**：未来必须遵循的团队选择；必须得到用户明确确认后才允许写入。
- **偏好原则**：协作方式或工程取向；仅当用户明确表达，且该原则能在未来任务中改变实际行为时保留。

无证据的存量项目结论不得表述为事实规则。它只能成为待确认的决策建议，或留在设计/计划中。

### 删除测试

在最终自检中，对每条拟写入 `.project/rules/` 的内容增加问题：

> 删除该条内容，是否会让后续 Agent 更可能在重要决策上犯错？

答案为“否”或无法说明具体错误时，不进入项目规则。该测试用于排除 KISS、DRY、代码整洁、及时测试等默认常识，以及没有行为影响的背景说明。

### 输出与写入边界

初筛输出从三类升级为四分流结果。项目规则候选必须包含：类型、证据、推荐落点、删除测试结论及推荐动作；项目索引或模块 README 候选使用同一元数据，但不以删除测试否决其稳定事实。

写入保持现有门禁：先向用户提交候选；确认后才更新已有最合适文件。若 `<repo>/.project/rules/` 不存在，禁止回退创建 `.claude/`、`.codex/` 或其他工具私有规则目录。

## 非目标

- 不把 `rule-refine` 扩展为从零重建根 `AGENTS.md` 或 `CLAUDE.md` 的工具。
- 不自动生成项目架构地图、模块 README 或任务设计文档。
- 不把实现细节、一次性经验或未证实愿望提升为规则。
- 不修改上游 `superpowers/`、`caveman/` 或 ai-tool 的同步机制。

## 验收标准

- skill 明确规定四种候选落点及其边界。
- skill 要求事实规则、决策规则和偏好原则的不同证据/确认条件。
- skill 要求拟写入项目规则的候选通过删除测试。
- 输出模板能展示证据、类型、落点与删除测试结论。
- 保留已有的去重、去具体化、反常识化、用户确认和工具中立路径约束。
