# Code Arch

## Overview

这个 skill 的核心不是固定画图，也不是固定输出调用链，而是**帮助用户理解他要求的那部分代码**。

默认做法是：**先总览，再按问题下钻，并用最有助于理解的表达方式输出。**

优先回答“这块代码整体怎么工作”，再根据用户真正关心的问题继续细化到业务流程、系统架构、关键代码路径、设计模式或缺点。不要一上来就展开类和方法细节。

## When to Use

在这些场景使用：
- 用户想理解某个功能、模块、服务或项目是怎么工作的
- 用户要求分析关键路径、核心流程、主链路或调用链
- 用户想看系统架构、模块关系、职责边界或核心组织方式
- 用户要求识别设计模式、设计取舍、扩展点或结构问题
- 用户在改代码前，想先弄清当前实现
- 用户想把分析整理成 markdown 文档

## Intent First

先判断用户真正要理解的是哪一层：
- **业务层**：功能整体怎么跑
- **系统层**：模块、角色、边界怎么协作
- **代码层**：入口、编排、关键调用链怎么串起来
- **问题层**：设计模式、缺点、风险、扩展点

如果用户的要求不明确，不要直接展开长文。先用一句话收窄，必要时给 1-3 个建议方向让用户选，例如：
- 更偏业务主流程
- 更偏系统架构关系
- 更偏关键代码调用链

## Core Working Method

### 1. 先总览

先回答这些问题：
- 这块代码整体在解决什么问题
- 主流程大致如何闭环
- 核心角色有哪些
- 哪几个节点最值得继续读

总览阶段只保留最关键的信息，不做类级穷举。

### 2. 再按需求细化

根据用户问题，下钻到最相关的层次：

#### 业务流程
优先找完整闭环：

`输入 / 触发 -> 入口 -> 编排 -> 核心处理 -> 外部交互 -> 输出 / 状态收口`

适合回答：
- “这个功能整体怎么跑？”
- “核心流程是什么？”
- “上传、确认、异步处理是怎么串起来的？”

#### 系统架构
优先说明：
- 关键角色
- 职责边界
- 依赖方向
- 协作关系

适合回答：
- “模块之间怎么协作？”
- “这个功能的核心架构是什么？”

#### 关键代码路径
只保留最关键的入口、编排节点和收口点，说明：
- 入口在哪里
- 谁负责主编排
- 核心决策在哪
- 谁负责持久化、外部交互或最终状态推进

适合回答：
- “从接口到落库怎么走？”
- “这条调用链的关键节点有哪些？”

#### 设计问题
只在用户关心或确实明显时展开：
- 设计模式
- 职责混杂
- 跨层调用
- 中心类过重
- 状态流转隐式
- 扩展点是否清晰
- 改动牵连面是否过大

## Expression Rules

表达方式必须服务于理解，不要固定模板。

根据问题选择最合适的输出：
- 需要快速理解整体：精简要点 + 小结
- 需要看主流程：流程图 / 时序图
- 需要看系统角色和边界：架构图 / 组件关系图
- 需要看关键代码路径：关键调用链或简化时序
- 需要沉淀内容：markdown 文档

### 关于图

图不是必选项，也不是固定版式。

只有在图能明显帮助理解时才画图；画图时选择最适合当前问题的图，不要机械固定为同一种图。

例如：
- 用户问“核心流程”时，优先业务流程图或系统流程图
- 用户问“系统怎么组织”时，优先架构关系图
- 用户问“代码怎么调用”时，优先关键调用链图

不要把图画成代码全量镜像，也不要为了画图而画图。

## Default Output Strategy

默认输出应为**精简到中等**，并根据用户原始要求自适应。

优先顺序：
1. 一段很短的总览
2. 最相关的一层主分析
3. 如有必要，再补第二层分析
4. 少量关键证据

常见优先级示例：
- 用户说“核心流程 / 关键路径” → 先业务流程或系统流程，再补关键代码路径
- 用户说“架构” → 先系统架构，再补关键流程
- 用户说“调用链” → 先关键代码路径，再补必要背景
- 用户说“设计问题” → 先总览，再集中讲模式、缺点和风险

不要默认输出：
- 大段类级说明
- 对每个方法逐条解释
- 与用户问题无关的次要分支
- 冗长背景铺垫

## Evidence Rules

所有关键结论尽量落到代码证据，优先引用真实位置，使用 `path:line` 形式。

但证据是为支撑结论，不是为了把所有看到的代码都列出来。

## Design Pattern Rules

只有在证据明确时才指出设计模式。

说明设计模式时必须同时给出：
- 证据：哪些类、接口或关系体现了它
- 价值：它解决了什么问题
- 代价：它引入了什么复杂度

如果证据不够强，就用保守说法，例如“呈现出类似 Strategy 的分发结构”。

## Output Contract

默认结构按需裁剪，不要求每次完整出现：

```md
# Code Architecture Analysis

## Scope
## Overview
## Core Flow / Architecture
## Key Code Path
## Design Notes
## Practical Reading Order
```

如果用户只要其中一部分，就只输出那部分和必要上下文。

## Ending Rule

如果用户没有明确要求直接生成 md 文件，在分析结尾主动问：

“要不要我把这份分析整理成一个 md 文件？”

## Common Mistakes

- 一上来就掉进类和方法细节，导致用户没建立整体理解
- 把“核心流程”错误理解成“类调用顺序”
- 图画成代码镜像，而不是理解工具
- 不区分业务流程、系统架构和代码路径，全部混在一起
- 文字过多，关键判断反而不突出
- 设计模式只报名词，不给证据和代价
