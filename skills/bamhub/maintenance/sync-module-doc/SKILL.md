# /sync-module-doc

目标：检查并同步指定模块的模块级 README.md，默认维护 `<module>/README.md`，确保它反映当前稳定实现，而不是过期描述。

## 适用场景

适用于以下场景：
- 某个模块完成了一轮代码或逻辑更新后，需要检查模块文档是否滞后
- 某个模块刚形成清晰主链路，但还没有模块级 `README.md`
- 某次重构、新增正式入口、职责边界调整后，需要同步模块约束
- 希望把本次会话中已经稳定下来的模块规则沉淀到模块文档中

不适用于：
- 只做了局部命名调整
- 只修了不影响主链路的小 bug
- 只是临时方案，还未形成稳定设计
- 只是想写一份 README 式说明文档

## 目标文档

默认维护目标：

- `模块目录/README.md`

这个命令维护模块 README 中面向协作者的稳定事实；不是记录任务过程，也不应把 README 扩写成实现流水账。README 应包含：
- 模块定位
- 核心主链路
- 少量关键流程图
- 分层边界
- 最容易改偏的点
- 修改时优先阅读
- 如何更新本文件

## 执行步骤

你必须按以下顺序执行：

1. **解析模块路径**
   - 读取用户提供的模块路径参数
   - 支持 `@bamboo-biz/bamboo-biz-ai/` 这种引用形式，也支持普通相对路径
   - 确认该目录真实存在

2. **判断是否适合作为独立模块维护文档**
   - 检查该目录是否具有明确模块边界（例如 `pom.xml`、稳定子目录结构、独立职责）
   - 如果该目录不适合作为独立模块维护 `README.md`，明确说明原因并停止，不要强行创建文档

3. **检查现有模块文档**
   - 优先检查 `模块目录/README.md`
   - 如果存在，先完整阅读
   - 如果不存在，不要立刻创建，先读代码判断是否值得创建

4. **阅读当前代码事实**
   必须先读代码，再决定文档是否要改。优先阅读：
   - 模块入口层
   - 核心主链路类
   - 本次改动涉及的关键文件
   - 如有必要，补充查看当前 diff 或最近相关提交

   阅读时使用以下方法论提升识别准确度：
   - **入口优先法**：先看外部入口，再看中枢编排，再看支撑服务，避免只看局部实现就下结论
   - **主链路闭环法**：按“输入 -> 编排 -> 执行 -> 输出/归档”检查是否形成完整闭环，不要只看单个类职责
   - **代码优先、文档校验法**：始终以当前代码为准，再反查现有 `README.md` 是否过期、过强、过弱或遗漏
   - **稳定性筛选法**：区分“长期稳定规则”和“本次实现细节”，只有前者才值得写进模块文档
   - **差异分级法**：把发现的问题分成“必须更新”“建议更新”“可选优化”三档，避免轻微措辞问题触发过度修改

   重点判断：
   - 模块定位是否变化
   - 核心主链路是否变化
   - 是否新增正式入口
   - run / history / context / archive / orchestration 等职责边界是否变化
   - 现有文档是否有与代码不一致之处
   - 本次会话中是否形成了值得长期保留的稳定规则

5. **判断是否需要更新文档**
   先把发现的问题分级，再决定动作：

   - **必须更新**：
     - 模块主链路变化
     - 新增正式入口
     - 关键职责边界变化
     - 文档已有结论与当前实现不一致
     - 本次会话明确沉淀了应长期保留的模块规则

   - **建议更新**：
     - 文档没有明显错误，但对关键约束表达不足
     - 新增了值得长期保留的易改偏点
     - 现有结构还能保持精简，但某一节明显缺失关键判断信息

   - **可选优化**：
     - 表述可以更准，但当前不构成误导
     - 某些措辞略强或略弱，但不影响后续主要实现判断
     - 结构还能更顺一点，但当前仍然清晰可用

   以下变化通常不要写入 `README.md`：
   - 临时任务目标
   - 一次性修复细节
   - 普通重构细节
   - 局部变量或方法重命名
   - 不影响后续实现判断的实现级变化
   - 还未稳定的尝试性实现

6. **创建或更新模块文档**
   - 如果没有 `README.md`：
     - 只有在确认该模块值得维护模块级文档时才创建
     - 使用精简、面向协作者的 README 结构
   - 如果已有 `README.md`：
     - 仅校准必要内容
     - 优先修改定位、主链路、边界、易偏离点、更新规则
     - 保持简短，不要因为一次改动把文档扩写成大篇幅说明

7. **输出同步结果**
   输出时必须明确说明：
   - 是否发现现有 `README.md`
   - 是否新建/更新/保持不变
   - 更新了哪些点
   - 哪些变化故意没有写入文档
   - 是否发现“可选优化项”但本次未修改
   - 当前文档是否仍保持精简

   试跑时要明确告诉用户：
   - “保持不变”也是有效结果，不代表命令无效
   - 如果本次没有达到“必须更新”或“建议更新”，应优先保持文档稳定
   - 对于只属于“可选优化”的问题，应单独列出，不要为了试跑强行改文档

## 文档结构要求

如果新建模块级 `README.md`，优先采用以下结构：

```md
# 模块名称

## 模块定位

## 核心主链路

## 核心流程图
### 1. 主流程
### 2. 第二主流程（如有）

## 分层边界

## 最容易改偏的点

## 修改时优先阅读

## 如何更新本文件
```

要求：
- 保持短，不写成任务过程或全量类清单
- 流程图只保留 1-2 个必要流程
- 不堆所有类清单
- 不记录一次性任务背景
- 只保留会影响后续实现判断的内容

## 更新原则

执行本命令时，默认遵守以下原则：

1. 先看代码，再改文档
2. 主链路没变就尽量少动
3. 只写稳定结论，不写临时结论
4. 文档不存在时优先创建 `README.md`
5. 如果该模块不适合维护模块级文档，要明确返回“不建议创建”
6. 这个命令应是“保守同步”，不是“自动扩写文档”

## 输出格式

默认按以下结构输出：

### 一、检查结果
- 模块路径
- 是否存在 `README.md`
- 是否适合维护模块级文档

### 二、同步动作
- 新建 / 更新 / 不变
- 本次修改的核心点

### 三、未写入文档的变化
- 哪些变化故意未写入
- 不写入的原因

### 四、可选优化项
- 发现了哪些可选优化项但本次未修改
- 为什么它们当前不属于必须更新或建议更新
- 是否建议下次顺手调整

### 五、当前结论
- 当前模块文档是否仍保持精简
- 本次结果属于：必须更新 / 建议更新 / 可选优化 / 保持不变
- 是否建议后续继续用该文档作为模块默认约束
