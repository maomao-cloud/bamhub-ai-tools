# /rule-refine

目标：把当前改动、讨论结论或指定文件中的经验，提炼成团队可长期遵守的规则，并在确认后更新到合适的规则文件中。

## 使用范围

适用于以下场景：
- 某次改动暴露出团队应统一遵守的实现原则
- 需要判断“这次经验是否值得写入规则”
- 需要把已有规则改写得更通用、更可执行
- 需要对比现有规则，避免重复新增

不适用于：
- 只总结本次任务过程
- 记录局部实现细节
- 没有复用价值的临时决定
- 仅适用于某个单一业务模块的特殊策略

## 规则准入筛选法

在生成候选规则前，必须先按以下顺序筛选：

1. **去重**
   - 先对比现有规则文件，判断该内容是否已经被覆盖：
     - `CLAUDE.md`
     - `.claude/rules/*.md`
   - 如果只是把现有规则换一种说法，不新增规则，优先建议改写原规则

2. **去特定化**
   - 去掉当前项目、模块、类名、方法名、字段名、本次实现细节
   - 不保留当前业务专属术语
   - 改写后应能脱离本次上下文单独成立

3. **去常识化**
   - 如果只是普通编码常识、命名建议、测试细节、局部实现技巧，不新增规则
   - 不把低价值、弱约束、人人都知道的内容写成团队规则

4. **保留长期价值**
   - 只保留值得团队在未来类似场景中持续遵守的内容
   - 应能跨模块复用，且能指导未来设计取舍
   - 如果只能解释本次实现，不新增规则

5. **通用化改写**
   - 改写成团队约束，而不是任务总结
   - 优先描述：
     - 什么场景下应该这样做
     - 什么场景下不应该这样做
     - 什么时候例外是合理的
   - 可给一个简单示例，但示例不得依赖当前项目上下文

6. **最终自检**
   - 生成候选规则后，必须再判断一次：
     - 这条规则是否真的值得团队长期承担维护成本？
     - 它是否能稳定指导未来多个类似场景？
     - 如果不能，则不新增规则

## 反例过滤

以下内容默认不应新增为规则，除非有非常强的长期复用价值：

- 只是把已有规则换个说法
- 只是本次具体实现经验
- 只是某个模块的局部策略
- 只是命名或代码整洁性的普通建议
- 只是模板、参数、落库、调用链等某类业务专属策略
- 只是测试写法或单次重构方式
- 没有长期复用价值的临时决定

如果某条内容落入以上情况，应归入：
- 已覆盖
- 不建议新增
- 建议改写原规则
而不是直接产出新规则

## 处理原则

1. 先对比现有规则，避免重复新增
2. 优先修改最合适的现有规则文件，而不是新增平行规则
3. 只有足够稳定、通用、值得长期遵守的内容，才建议写入规则
4. 规则文案必须：
   - 通用
   - 可执行
   - 非项目特定
   - 不依赖本次会话背景
5. 不为了凑规则而新增规则
6. 如果只是现有规则表达不够好，优先建议重写原规则

## 执行步骤

1. 读取当前相关上下文：
   - 当前会话结论
   - 用户明确强调的问题
   - 指定文件或相关改动（如果提供参数）

2. 对比现有规则，先输出三类初筛结果：
   - 已被现有规则覆盖
   - 不建议新增为规则
   - 值得进入候选规则筛选的内容

3. 只对通过初筛的内容继续处理：
   - 去项目特定化
   - 去实现细节化
   - 去常识化
   - 改写为通用、可执行的团队规则表述

4. 对每条候选规则补充判断：
   - 为什么值得纳入
   - 为什么可能不值得纳入
   - 与现有规则是否重复
   - 应新增还是改写原规则

5. 先把候选规则列表发给用户确认，不要直接改文件

6. 用户确认后，再更新对应规则文件：
   - 优先修改最合适的现有规则文件
   - 非必要不新增规则文件
   - 保持原文件风格与章节语气一致

## 输出格式

默认按以下结构输出：

### 一、已覆盖内容
- 哪些点已被现有规则覆盖
- 为什么不建议重复新增

### 二、不建议新增内容
- 哪些点不值得写成规则
- 原因是什么
- 是否只是本次实现细节、局部策略或普通常识

### 三、候选规则
对每条候选规则，固定输出：
- 候选标题
- 是否建议纳入
- 纳入原因
- 不纳入风险或反方判断
- 与现有规则是否重复
- 推荐动作：新增 / 改写原规则 / 不处理
- 通用化后的规则文案
- 如有必要，附一个简单示例

### 四、建议落点
- 推荐更新的规则文件
- 推荐放置的章节
- 为什么放这里最合适

### 五、待确认项
- 需要用户确认保留、删减或调整的内容

## 写入规则文件时的要求

- 不新增与现有规则语义重复的条目
- 不写成“本次项目里怎么做”
- 不写成“某个类/方法应该怎样”
- 不写成实现说明、任务总结或变更记录
- 应写成未来团队在类似场景下都能直接采用的规则

## 判断标准

只有同时满足以下条件，才可作为新增团队规则候选：
- 能跨模块复用
- 能指导未来类似设计取舍
- 不依赖当前项目特定类名或术语
- 不是一次性实现细节
- 不是普通编码常识
- 值得团队长期遵守

如果有任一条件不满足，优先归入：
- 已覆盖
- 不建议新增
- 建议改写原规则

## 示例任务理解

如果当前改动暴露出以下问题：
- 同一业务规则在不同入口各写一套
- 同一份数据在多个后续环节各自加工导致不一致
- 边界适配和核心规则混在一起

则应优先尝试判断：
- 这些内容是否已被现有规则覆盖
- 是否真的值得新增团队规则
- 是否更适合改写原有“分层 / 核心链路收敛 / 对象边界”相关规则
- 如何改写成不依赖当前业务上下文的通用规则
